# عامل‌های هوش مصنوعی و مدل‌های زبان کوچک: یک راهنمای جامع

## مقدمه

در این آموزش، به بررسی عامل‌های هوش مصنوعی و مدل‌های زبان کوچک (SLMها) و استراتژی‌های پیشرفته پیاده‌سازی آن‌ها برای محیط‌های محاسبات لبه‌ای خواهیم پرداخت. مفاهیم پایه هوش مصنوعی عاملی، تکنیک‌های بهینه‌سازی SLM، استراتژی‌های کاربردی برای استقرار روی دستگاه‌های با منابع محدود، و Microsoft Agent Framework برای ساخت سیستم‌های آماده تولید عامل را پوشش خواهیم داد.

چشم‌انداز هوش مصنوعی در سال ۲۰۲۵ دچار تغییر پارادایمی شده است. در حالی که سال ۲۰۲۳ سال چت‌بات‌ها و ۲۰۲۴ سال افزایش چشمگیر همیارهای هوشمند بود، سال ۲۰۲۵ متعلق به عامل‌های هوش مصنوعی است — سیستم‌های هوشمندی که فکر می‌کنند، استدلال می‌کنند، برنامه‌ریزی می‌کنند، ابزارها را به کار می‌برند و وظایف را با حداقل دخالت انسان اجرا می‌کنند، که به طور فزاینده‌ای توسط مدل‌های زبان کوچک کارآمد پشتیبانی می‌شوند. Microsoft Agent Framework به عنوان یک راه‌حل پیشرو برای ساخت این سیستم‌های هوشمند با قابلیت‌های آفلاین مبتنی بر لبه مطرح شده است.

## درک عامل‌های هوش مصنوعی: مبانی و دسته‌بندی‌ها

### تعریف و مفاهیم اصلی

عامل هوش مصنوعی (AI) به سیستمی یا برنامه‌ای گفته می‌شود که قادر است به طور مستقل وظایفی را به نمایندگی از یک کاربر یا سیستم دیگر انجام دهد، با طراحی جریان کاری خود و استفاده از ابزارهای موجود. بر خلاف هوش مصنوعی سنتی که تنها به سوالات شما پاسخ می‌دهد، عامل می‌تواند به طور مستقل عمل کند تا اهداف را محقق سازد.

### چارچوب دسته‌بندی عامل‌ها

درک مرزهای عامل به انتخاب نوع مناسب عامل برای سناریوهای مختلف محاسباتی کمک می‌کند:

- **🔬 عامل‌های واکنشی ساده**: سیستم‌های مبتنی بر قانون که به درک‌های فوری پاسخ می‌دهند (ترموستات‌ها، اتوماسیون پایه)
- **📱 عامل‌های مبتنی بر مدل**: سیستم‌هایی که حالت داخلی و حافظه را نگه می‌دارند (جاروبرقی‌های رباتیک، سیستم‌های ناوبری)
- **⚖️ عامل‌های مبتنی بر هدف**: سیستم‌هایی که توالی‌هایی را برای دست‌یابی به اهداف برنامه‌ریزی و اجرا می‌کنند (برنامه‌ریزهای مسیر، زمان‌بندهای وظایف)
- **🧠 عامل‌های یادگیرنده**: سیستم‌های تطبیقی که عملکرد خود را با زمان بهبود می‌بخشند (سیستم‌های توصیه‌گر، دستیاران شخصی)

### مزایای کلیدی عامل‌های هوش مصنوعی

عامل‌های هوش مصنوعی چند مزیت اساسی دارند که آن‌ها را برای کاربردهای محاسبات لبه‌ای ایده‌آل می‌کند:

**خودمختاری عملیاتی**: عامل‌ها اجرای مستقل وظایف را بدون نظارت مداوم انسان فراهم می‌کنند، که آن‌ها را برای کاربردهای زمان واقعی ایده‌آل می‌سازد. آن‌ها به حداقل نظارت نیاز دارند و در عین حال رفتار تطبیقی دارند که امکان استقرار روی دستگاه‌های محدود را با بار عملیاتی کمتر فراهم می‌کند.

**انعطاف‌پذیری در استقرار**: این سیستم‌ها قابلیت‌های هوش مصنوعی روی دستگاه بدون نیاز به اتصال اینترنت را فراهم می‌کنند، از حریم خصوصی و امنیت از طریق پردازش محلی محافظت می‌کنند، برای کاربردهای مرتبط با حوزه خاص قابل سفارشی‌سازی هستند و برای محیط‌های مختلف محاسبات لبه‌ای مناسب‌اند.

**صرفه‌جویی در هزینه‌ها**: سیستم‌های عامل نسبت به راه‌حل‌های مبتنی بر ابر هزینه کمتری برای استقرار ارائه می‌دهند، با کاهش هزینه‌های عملیاتی و نیاز به پهنای باند کمتر برای کاربردهای لبه‌ای.

## استراتژی‌های پیشرفته مدل زبان کوچک

### مبانی SLM (مدل زبان کوچک)

مدل زبان کوچک (SLM) مدلی است که می‌تواند روی یک دستگاه الکترونیکی مصرفی معمولی قرار گیرد و با تأخیر کم به میزان کافی برای پاسخ به درخواست‌های عاملی یک کاربر عمل کند. به بیان عملی، SLMها معمولاً مدل‌هایی با کمتر از ۱۰ میلیارد پارامتر هستند.

**ویژگی‌های کشف فرمت**: SLMها پشتیبانی پیشرفته‌ای برای سطوح مختلف کمّی‌سازی، سازگاری بین‌پلتفرمی، بهینه‌سازی عملکرد زمان واقعی، و قابلیت‌های استقرار لبه‌ای ارائه می‌کنند. کاربران می‌توانند از حریم خصوصی ارتقا یافته از طریق پردازش محلی و پشتیبانی WebGPU برای استقرار در مرورگر بهره‌مند شوند.

**مجموعه سطوح کمّی‌سازی**: فرمت‌های محبوب SLM شامل Q4_K_M برای فشرده‌سازی متعادل در کاربردهای موبایل، سری Q5_K_S برای استقرار کیفیت‌محور در لبه، Q8_0 برای دقت نزدیک به اصل روی دستگاه‌های قدرتمند لبه، و فرمت‌های آزمایشی مانند Q2_K برای سناریوهای با منابع بسیار کم است.

### GGUF (فرمت عمومی جهانی GGML) برای استقرار SLM

GGUF به عنوان فرمت اصلی برای استقرار SLMهای کمّی‌سازی شده روی CPU و دستگاه‌های لبه‌ای خدمت می‌کند، که به خصوص برای کاربردهای عاملی بهینه شده است:

**ویژگی‌های بهینه شده برای عامل**: این فرمت منابع جامعی برای تبدیل و استقرار SLM با پشتیبانی پیشرفته از فراخوانی ابزار، تولید خروجی ساختاریافته و مکالمات چندمرحله‌ای فراهم می‌آورد. سازگاری بین‌پلتفرمی رفتار مداوم عامل را در دستگاه‌های مختلف لبه تضمین می‌کند.

**بهینه‌سازی عملکرد**: GGUF امکان استفاده بهینه از حافظه برای جریان‌های کاری عامل، پشتیبانی از بارگذاری پویا مدل برای سیستم‌های چندعاملی، و استنتاج بهینه شده برای تعاملات بلادرنگ عامل را فراهم می‌کند.

### چارچوب‌های بهینه‌شده برای لبه SLM

#### بهینه‌سازی Llama.cpp برای عامل‌ها

Llama.cpp تکنیک‌های پیشرفته کمّی‌سازی را مخصوص استقرار SLM عاملی ارائه می‌دهد:

**کمّی‌سازی مخصوص عامل**: این چارچوب از Q4_0 (بهینه برای استقرار عامل موبایل با ۷۵٪ کاهش اندازه)، Q5_1 (کیفیت-فشرده‌سازی متعادل برای عامل‌های استنتاج لبه) و Q8_0 (کیفیت نزدیک به اصل برای سیستم‌های عامل تولید) پشتیبانی می‌کند. فرمت‌های پیشرفته امکان عامل‌های فوق فشرده برای سناریوهای لبه‌ای شدید فراهم می‌کنند.

**مزایای پیاده‌سازی**: استنتاج بهینه‌شده CPU با شتاب SIMD اجرای عامل کم‌حافظه را فراهم می‌کند. سازگاری بین‌پلتفرمی در معماری‌های x86، ARM و Apple Silicon امکان استقرار جهانی عامل را فراهم می‌آورد.

#### چارچوب Apple MLX برای عامل‌های SLM

Apple MLX بهینه‌سازی‌های بومی مخصوص عامل‌های مبتنی بر SLM روی دستگاه‌های Apple Silicon ارائه می‌دهد:

**بهینه‌سازی عامل برای Apple Silicon**: این چارچوب از معماری حافظه یکپارچه با ادغام Metal Performance Shaders، دقت مخلوط خودکار برای استنتاج عامل، و پهنای باند حافظه بهینه شده برای سیستم‌های چندعاملی استفاده می‌کند. عامل‌های SLM روی چیپ‌های سری M عملکرد استثنایی دارند.

**ویژگی‌های توسعه**: پشتیبانی API از Python و Swift با بهینه‌سازی‌های خاص عامل، مشتق‌گیری خودکار برای یادگیری عامل، و یکپارچگی بی‌وقفه با ابزارهای توسعه اپل محیط‌های توسعه جامع عامل را فراهم می‌کنند.

#### ONNX Runtime برای عامل‌های SLM چندپلتفرمی

ONNX Runtime یک موتور استنتاج جهانی فراهم می‌کند که اجرای مداوم عامل‌های SLM را در سخت‌افزارها و سیستم‌عامل‌های متنوع امکان‌پذیر می‌سازد:

**استقرار جهانی**: ONNX Runtime رفتار مداوم عامل‌های SLM را روی پلتفرم‌های Windows، Linux، macOS، iOS و Android تضمین می‌کند. این سازگاری چندپلتفرمی به توسعه‌دهندگان اجازه می‌دهد یک بار کد بنویسند و در همه جا مستقر کنند، و به طور قابل توجهی هزینه توسعه و نگهداری برنامه‌های چندپلتفرمی را کاهش می‌دهد.

**گزینه‌های شتاب سخت‌افزاری**: این چارچوب ارائه‌دهندگان اجرای بهینه‌شده برای پیکربندی‌های مختلف سخت‌افزاری از جمله CPU (Intel، AMD، ARM)، GPU (NVIDIA CUDA، AMD ROCm) و شتاب‌دهنده‌های تخصصی (Intel VPU، Qualcomm NPU) دارد. عامل‌های SLM می‌توانند به طور خودکار از بهترین سخت‌افزار موجود بدون تغییر کد استفاده کنند.

**ویژگی‌های آماده تولید**: ONNX Runtime ویژگی‌های سازمانی ضروری برای استقرار عامل‌های تولیدی را فراهم می‌کند، از جمله بهینه‌سازی گراف برای استنتاج سریع‌تر، مدیریت حافظه برای محیط‌های محدود، و ابزارهای جامع پروفایل‌گیری برای تحلیل عملکرد. این چارچوب از APIهای Python و C++ برای ادغام انعطاف‌پذیر پشتیبانی می‌کند.


## مقایسه پیشرفته SLM و LLM در سیستم‌های عاملی

### مزایای SLM در کاربردهای عاملی

**کارایی عملیاتی**: SLMها نسبت به LLMها در وظایف عاملی کاهش هزینه ۱۰-۳۰ برابری ارائه می‌دهند، و پاسخ‌های بلادرنگ عاملی در مقیاس را امکان‌پذیر می‌سازند. زمان‌های استنتاج سریع‌تری به دلیل کاهش پیچیدگی محاسباتی دارند، که آن‌ها را برای کاربردهای تعاملی عاملی ایده‌آل می‌کند.

**قابلیت‌های استقرار در لبه**: SLMها اجرای عامل روی دستگاه بدون وابستگی به اینترنت، افزایش حریم خصوصی از طریق پردازش محلی، و سفارشی‌سازی برای کاربردهای حوزه‌محور عامل که برای محیط‌های متنوع محاسبات لبه‌ای مناسب است، فراهم می‌کنند.

**بهینه‌سازی مخصوص عامل**: SLMها در فراخوانی ابزار، تولید خروجی ساختاریافته، و جریان‌های کاری تصمیم‌گیری روتین که ۷۰-۸۰٪ وظایف معمول عامل را تشکیل می‌دهند، عملکرد برتری دارند.

### چه زمانی از SLM و چه زمانی از LLM در سیستم‌های عاملی استفاده کنیم

**برای SLMها مناسب است**:
- **وظایف تکراری عامل**: ورود داده‌ها، پرکردن فرم‌ها، فراخوانی‌های روتین API
- **یکپارچه‌سازی ابزار**: پرس‌وجوهای پایگاه داده، عملیات فایل، تعاملات سیستمی
- **جریان‌های کاری ساختاریافته**: دنبال کردن فرآیندهای تعریفی عامل
- **عامل‌های حوزه‌محور**: خدمات مشتری، زمان‌بندی، تحلیل‌های پایه
- **پردازش محلی**: عملیات عامل حساس به حریم خصوصی

**برای LLMها مناسب‌تر است**:
- **استدلال پیچیده**: حل مسئله نوآورانه، برنامه‌ریزی استراتژیک
- **مکالمات باز و گسترده**: چت عمومی، مباحث خلاقانه
- **وظایف دانش گسترده**: پژوهش نیازمند دانش عمومی وسیع
- **سناریوهای نو**: مدیریت سناریوهای کاملاً جدید عامل

### معماری ترکیبی عامل

رویکرد بهینه ترکیب SLM و LLM در سیستم‌های عاملی ناهمگون است:

**هماهنگی هوشمند عامل‌ها**:
1. **SLM به عنوان اصلی**: مدیریت ۷۰-۸۰٪ وظایف روتین عامل به صورت محلی
2. **LLM در مواقع ضروری**: هدایت پرسش‌های پیچیده به مدل‌های بزرگ مبتنی بر ابر
3. **SLMهای تخصصی**: مدل‌های کوچک مختلف برای حوزه‌های مختلف عامل
4. **بهینه‌سازی هزینه**: حداقل کردن فراخوانی‌های پرهزینه LLM با مسیر‌یابی هوشمند

## استراتژی‌های استقرار عامل SLM تولیدی

### Foundry Local: محیط اجرای هوش مصنوعی لبه‌ای سازمانی

Foundry Local (https://github.com/microsoft/foundry-local) به عنوان راه‌حل اصلی مایکروسافت برای استقرار مدل‌های زبان کوچک در محیط‌های تولیدی لبه‌ای خدمت می‌کند. این محیط اجرای کامل و مخصوص عامل‌های مبتنی بر SLM با ویژگی‌های سطح سازمانی و قابلیت‌های یکپارچه‌سازی بدون درز را فراهم می‌کند.

**معماری اصلی و ویژگی‌ها**:
- **API سازگار با OpenAI**: تطابق کامل با SDK و یکپارچه‌سازی‌های Agent Framework
- **بهینه‌سازی خودکار سخت‌افزار**: انتخاب هوشمندانه مدل‌های متنوع بر اساس سخت‌افزار موجود (GPUهای CUDA، NPU کوالکام، CPU)
- **مدیریت مدل**: دانلود خودکار، کشینگ و مدیریت چرخه عمر مدل‌های SLM
- **کشف خدمات**: شناسایی سرویس بدون پیکربندی برای فریم‌ورک‌های عاملی
- **بهینه‌سازی منابع**: مدیریت هوشمند حافظه و کارآمدی توان برای استقرار لبه‌ای

#### نصب و راه‌اندازی

**نصب چندپلتفرمی**:
```bash

winget install Microsoft.FoundryLocal

# مک‌اواس

tar -xzf foundry-local-linux.tar.gz

```

**شروع سریع برای توسعه عامل**:
```bash

# بررسی وضعیت سرویس و نقطه انتهایی
foundry service status

# فهرست مدل‌های موجود
foundry model ls

# آزمایش نقطه انتهایی API
curl http://localhost:<port>/v1/models
```

#### یکپارچه‌سازی فریم‌ورک عامل

**یکپارچه‌سازی SDK Foundry Local**:
```python
from foundry_local import FoundryLocalManager
from microsoft_agent_framework import Agent, Config
import openai

# مقداردهی اولیه Foundry Local با مدیریت خودکار سرویس
manager = FoundryLocalManager("phi-4-mini")

# پیکربندی کلاینت OpenAI برای استنتاج محلی
client = openai.OpenAI(
    base_url=manager.endpoint,
    api_key=manager.api_key  # به طور خودکار برای استفاده محلی ایجاد شده است
)

# ایجاد عامل با بخش پشتی Foundry Local
agent_config = Config(
    name="production-agent",
    model_provider="foundry-local",
    model_id=manager.get_model_info("phi-4-mini").id,
    endpoint=manager.endpoint,
    api_key=manager.api_key
)

agent = Agent(config=agent_config)
```

```python
            "total_models": total_models,
```

```python
class FoundryResourceManager:
    def __init__(self):
        self.model_instances = {}
        self.resource_limits = {
            "max_memory_gb": 8,
            "max_concurrent_models": 3,
            "cpu_threshold": 80
        }
    
    def auto_scale_models(self, demand_metrics: dict):
        """Automatically scale models based on demand."""
        current_memory = self.get_total_memory_usage()
        
        # در صورت استفاده زیاد از حافظه، مقیاس‌بندی را کاهش دهید
        if current_memory > self.resource_limits["max_memory_gb"] * 0.8:
            self.scale_down_idle_models()
        
        # در صورت تقاضای بالا و وجود منابع، مقیاس‌بندی را افزایش دهید
        for model_alias, demand in demand_metrics.items():
            if demand > 0.8 and len(self.model_instances) < self.resource_limits["max_concurrent_models"]:
                self.load_model_instance(model_alias)
    
    def load_model_instance(self, alias: str) -> FoundryLocalManager:
        """Load a new model instance if resources allow."""
        if alias not in self.model_instances:
            try:
                manager = FoundryLocalManager(alias)
                self.model_instances[alias] = manager
                logging.info(f"Loaded model instance: {alias}")
                return manager
            except Exception as e:
                logging.error(f"Failed to load model {alias}: {e}")
                return None
        return self.model_instances[alias]
    
    def scale_down_idle_models(self):
        """Remove idle model instances to free resources."""
        idle_models = []
        
        for alias, manager in self.model_instances.items():
            if manager.get_idle_time() > 300:  # ۵ دقیقه بیکاری
                idle_models.append(alias)
        
        for alias in idle_models:
            self.model_instances[alias].shutdown()
            del self.model_instances[alias]
            logging.info(f"Scaled down idle model: {alias}")
```

```python
                logging.info(f"Initialized {agent_type} agent with model {model_name}")

        try:
            # بررسی وجود مدل
            response = requests.get(f"{self.base_url}/api/tags")
            models = response.json().get('models', [])
            
            model_exists = any(model['name'] == model_name for model in models)
            
            if not model_exists:
                logging.info(f"Pulling model {model_name}...")
                pull_response = requests.post(f"{self.base_url}/api/pull", 
                    json={"name": model_name})
                
                if pull_response.status_code != 200:
                    raise Exception(f"Failed to pull model {model_name}")

            raise Exception(f"Model setup failed for {model_name}: {e}")

                """Search technical knowledge base."""
                return f"Knowledge base results for: {query}"
    
    async def process_request(self, request: str, agent_type: str = "customer_service") -> dict:
        """Process user request with monitoring and error handling."""
        start_time = time.time()
        
        try:
            if agent_type not in self.agents:
                raise ValueError(f"Agent type {agent_type} not available")
            
            agent = self.agents[agent_type]
            response = await agent.chat_async(request)
            
            # به‌روزرسانی معیارها
            self.metrics["requests_processed"] += 1
            self.metrics["model_usage"][agent_type] += 1
            
            processing_time = time.time() - start_time
            
            self._log_interaction(request, response, "success", processing_time, agent_type)
            
            return {
                "response": response,
                "status": "success",
                "processing_time": processing_time,
                "agent_type": agent_type
            }
            
        except Exception as e:
            self.metrics["errors"] += 1
            processing_time = time.time() - start_time
            
            self._log_interaction(request, str(e), "error", processing_time, agent_type)
            
            return {
                "response": "I'm experiencing technical difficulties. Please try again.",
                "status": "error",
                "error": str(e),
                "processing_time": processing_time
            }
    
    def _log_interaction(self, request: str, response: str, status: str, 
                        processing_time: float, agent_type: str):
        """Log interaction for monitoring and analysis."""
        logging.info(f"Agent: {agent_type}, Status: {status}, Time: {processing_time:.2f}s")
        
        # در تولید، این به سیستم ثبت مناسب می‌نویسد
        log_entry = {
            "timestamp": time.time(),
            "agent_type": agent_type,
            "request_length": len(request),
            "response_length": len(response),
            "status": status,
            "processing_time": processing_time
        }
    
    def get_health_status(self) -> dict:
        """Get service health status."""
        try:
            # بررسی سلامت سرویس اولاما
            response = requests.get(f"{self.base_url}/api/tags", timeout=5)
            ollama_healthy = response.status_code == 200
            
            # بررسی در دسترس بودن مدل
            available_models = []
            if ollama_healthy:
                models = response.json().get('models', [])
                available_models = [model['name'] for model in models]
            
            return {
                "service_status": "healthy" if ollama_healthy else "unhealthy",
                "ollama_endpoint": self.base_url,
                "available_models": available_models,
                "active_agents": list(self.agents.keys()),
                "metrics": self.metrics,
                "timestamp": time.time()
            }
            
        except Exception as e:
            return {
                "service_status": "error",
                "error": str(e),
                "timestamp": time.time()
            }
```

```python
    async def collect_metrics(self) -> dict:
        """Collect comprehensive metrics from Ollama service."""
        metrics = {
            "timestamp": time.time(),
            "service_status": "unknown",
            "models": {},
            "performance": {},
            "resources": {}
        }
        
        try:
            # بررسی سلامت سرویس
            health_response = requests.get(f"{self.base_url}/api/tags", timeout=5)
            metrics["service_status"] = "healthy" if health_response.status_code == 200 else "unhealthy"
            
            if metrics["service_status"] == "healthy":
                # دریافت اطلاعات مدل
                models_data = health_response.json().get('models', [])
                for model in models_data:
                    model_name = model['name']
                    metrics["models"][model_name] = {
                        "size_gb": model.get('size', 0) / (1024**3),
                        "modified": model.get('modified_at', ''),
                        "digest": model.get('digest', '')[:12]  # خلاصه کوتاه
                    }
                
                # آزمایش عملکرد استنتاج
                start_time = time.time()
                test_response = requests.post(f"{self.base_url}/api/generate", 
                    json={
                        "model": list(metrics["models"].keys())[0] if metrics["models"] else "",
                        "prompt": "Hello",
                        "stream": False
                    }, timeout=10)
                
                if test_response.status_code == 200:
                    inference_time = (time.time() - start_time) * 1000
                    metrics["performance"] = {
                        "inference_time_ms": inference_time,
                        "tokens_per_second": self._calculate_tokens_per_second(test_response.json()),
                        "last_successful_inference": time.time()
                    }
            
        except Exception as e:
            metrics["service_status"] = "error"
            metrics["error"] = str(e)
        
        self.metrics_history.append(metrics)
        
        # نگهداری تنها ۱۰۰ ورودی آخر معیارها
        if len(self.metrics_history) > 100:
            self.metrics_history = self.metrics_history[-100:]
        
        return metrics
    
    def _calculate_tokens_per_second(self, response_data: dict) -> float:
        """Calculate approximate tokens per second from response."""
        try:
            # تخمین توکن‌ها (برآورد تقریبی)
            response_text = response_data.get('response', '')
            estimated_tokens = len(response_text.split())
            
            # دریافت اطلاعات زمان‌بندی در صورت موجود بودن
            eval_duration = response_data.get('eval_duration', 0)
            if eval_duration > 0:
                # تبدیل نانوثانیه به ثانیه
                duration_seconds = eval_duration / 1e9
                return estimated_tokens / duration_seconds if duration_seconds > 0 else 0
        except:
            pass
        return 0
    
    def check_alerts(self, current_metrics: dict) -> List[dict]:
        """Check current metrics against alert thresholds."""
        alerts = []
        
        # بررسی زمان پاسخ
        if current_metrics.get('performance', {}).get('inference_time_ms', 0) > self.alert_thresholds['response_time_ms']:
            alerts.append({
                "type": "performance",
                "message": f"High response time: {current_metrics['performance']['inference_time_ms']:.0f}ms",
                "severity": "warning"
            })
        
        # بررسی وضعیت سرویس
        if current_metrics.get('service_status') != 'healthy':
            alerts.append({
                "type": "availability",
                "message": f"Service unhealthy: {current_metrics.get('error', 'Unknown error')}",
                "severity": "critical"
            })
        
        return alerts
    
    def get_performance_summary(self, minutes: int = 60) -> dict:
        """Get performance summary for the last N minutes."""
        cutoff_time = time.time() - (minutes * 60)
        recent_metrics = [m for m in self.metrics_history if m['timestamp'] > cutoff_time]
        
        if not recent_metrics:
            return {"error": "No recent metrics available"}
        
        # محاسبه میانگین‌ها
        response_times = [m.get('performance', {}).get('inference_time_ms', 0) 
                         for m in recent_metrics if m.get('performance')]
        
        healthy_checks = sum(1 for m in recent_metrics if m.get('service_status') == 'healthy')
        uptime_percent = (healthy_checks / len(recent_metrics)) * 100 if recent_metrics else 0
        
        return {
            "period_minutes": minutes,
            "total_checks": len(recent_metrics),
            "uptime_percent": uptime_percent,
            "avg_response_time_ms": sum(response_times) / len(response_times) if response_times else 0,
            "max_response_time_ms": max(response_times) if response_times else 0,
            "min_response_time_ms": min(response_times) if response_times else 0
        }
```

```python
from microsoft_agent_framework import Agent, Config
import openai
import subprocess
import time
import requests
from typing import Optional, Dict, Any

class VLLMManager:
    def __init__(self, model_name: str, 
                 host: str = "localhost", 
                 port: int = 8000,
                 gpu_memory_utilization: float = 0.8,
                 max_model_len: int = 4096):
        self.model_name = model_name
        self.host = host
        self.port = port
        self.base_url = f"http://{host}:{port}"
        self.gpu_memory_utilization = gpu_memory_utilization
        self.max_model_len = max_model_len
        self.process = None
        self.client = None
        
    def start_server(self) -> bool:
        """Start VLLM server with optimized settings for agents."""
        try:
            cmd = [
                "python", "-m", "vllm.entrypoints.openai.api_server",
                "--model", self.model_name,
                "--host", self.host,
                "--port", str(self.port),
                "--gpu-memory-utilization", str(self.gpu_memory_utilization),
                "--max-model-len", str(self.max_model_len),
                "--trust-remote-code",
                "--disable-log-requests",  # کاهش لاگ‌گیری برای عوامل
                "--served-model-name", self.get_served_model_name()
            ]
            
            self.process = subprocess.Popen(cmd, 
                stdout=subprocess.PIPE, 
                stderr=subprocess.PIPE)
            
            # انتظار برای شروع سرور
            max_retries = 30
            for _ in range(max_retries):
                if self.health_check():
                    self.client = openai.OpenAI(base_url=f"{self.base_url}/v1")
                    return True
                time.sleep(2)
                
            return False
            
        except Exception as e:
            print(f"Failed to start VLLM server: {e}")
            return False
    
    def get_served_model_name(self) -> str:
        """Get a clean model name for serving."""
        return self.model_name.replace("/", "--")
    
    def health_check(self) -> bool:
        """Check if VLLM server is healthy."""
        try:
            response = requests.get(f"{self.base_url}/health", timeout=5)
            return response.status_code == 200
        except:
            return False
    
    def get_openai_client(self) -> openai.OpenAI:
        """Get OpenAI-compatible client for VLLM."""
        if not self.client:
            self.client = openai.OpenAI(base_url=f"{self.base_url}/v1")
        return self.client
    
    def get_model_info(self) -> Dict[str, Any]:
        """Get model information and statistics."""
        try:
            response = requests.get(f"{self.base_url}/v1/models")
            if response.status_code == 200:
                return response.json()
        except:
            pass
        return {}
    
    def shutdown(self):
        """Shutdown VLLM server."""
        if self.process:
            self.process.terminate()
            self.process.wait()
```

```python
                        "worker_id": worker_id
                    }
                    
                    request_future.set_result(result)

                    request_future.set_exception(e)
```

```python
                    "avg_latency_ms": sum(m.average_latency_ms for m in instance_metrics) / len(instance_metrics),
                    "max_latency_ms": max(m.average_latency_ms for m in instance_metrics),
                    "avg_gpu_utilization": sum(m.gpu_utilization_percent for m in instance_metrics) / len(instance_metrics),
                    "avg_requests_per_second": sum(m.requests_per_second for m in instance_metrics) / len(instance_metrics),
                    "max_queue_length": max(m.queue_length for m in instance_metrics),
                    "availability_percent": (len(instance_metrics) / len(recent_metrics)) * 100
                }
        
        return report
    
    async def auto_scaling_recommendations(self) -> List[dict]:
        """Generate auto-scaling recommendations based on performance metrics."""
        recommendations = []
        
        if not self.metrics_history:
            return recommendations
        
        latest_metrics = self.metrics_history[-1]
        
        for instance_name, metrics in latest_metrics.items():
            # توصیه مربوط به تأخیر بالا
            if metrics.average_latency_ms > self.alert_thresholds["latency_max_ms"]:
                recommendations.append({
                    "instance": instance_name,
                    "type": "scale_up",
                    "reason": f"High latency: {metrics.average_latency_ms:.0f}ms",
                    "suggestion": "Consider adding tensor parallelism or increasing GPU memory"
                })
            
            # توصیه مربوط به استفاده بالای GPU
            if metrics.gpu_utilization_percent > self.alert_thresholds["gpu_utilization_max"]:
                recommendations.append({
                    "instance": instance_name,
                    "type": "scale_out",
                    "reason": f"High GPU utilization: {metrics.gpu_utilization_percent:.1f}%",
                    "suggestion": "Consider adding additional GPU instances"
                })
            
            # توصیه مربوط به استفاده پایین
            if (metrics.gpu_utilization_percent < 20 and 
                metrics.requests_per_second < 1):
                recommendations.append({
                    "instance": instance_name,
                    "type": "scale_down",
                    "reason": f"Low utilization: {metrics.gpu_utilization_percent:.1f}% GPU, {metrics.requests_per_second:.1f} RPS",
                    "suggestion": "Consider consolidating workloads or reducing resources"
                })
        
        return recommendations
```

```python
orchestrator = AgentOrchestrator([
    scheduling_agent,
    technical_support_agent

    routing_strategy="intent-based"
```

### بهترین روش‌ها برای چارچوب عامل مایکروسافت

#### دستورالعمل‌های توسعه

1. **شروع ساده**: ابتدا با سناریوهای تک‌عاملی آغاز کنید قبل از ساخت سیستم‌های چندعاملی پیچیده

4. **امنیت اول**: کنترل‌های امنیتی را از ابتدا اجرا کنید، نه به عنوان فکر آخر
5. **مستندسازی**: مستندات روشن از قابلیت‌ها و محدودیت‌های عامل‌ها نگهداری کنید

## تبدیل عملی و موارد استفاده عامل SLM

### سناریوهای استقرار عامل در دنیای واقعی

**برنامه‌های عامل موبایل**: فرمت‌های Q4_K در برنامه‌های عامل گوشی‌های هوشمند با حداقل حافظه مصرفی عالی عمل می‌کنند، در حالی که Q8_0 عملکرد متعادلی برای سیستم‌های عامل مبتنی بر تبلت ارائه می‌دهد. فرمت‌های Q5_K کیفیت برتری برای عوامل تولیدی موبایل دارند.

**محاسبات عامل دسکتاپ و لبه**: Q5_K بهترین عملکرد را برای برنامه‌های عامل دسکتاپ ارائه می‌کند، Q8_0 استنتاج با کیفیت بالا برای محیط‌های عامل workstation فراهم می‌کند، و Q4_K پردازش بهینه را روی دستگاه‌های عامل لبه امکان‌پذیر می‌سازد.

**عوامل تحقیقاتی و آزمایشی**: فرمت‌های کوانتیزاسیون پیشرفته امکان بررسی استنتاج عامل با دقت بسیار پایین برای تحقیقات دانشگاهی و برنامه‌های اثبات مفهوم عامل که نیازمند محدودیت‌های شدید منابع هستند را می‌دهند.

### بنچمارک‌های عملکرد عامل SLM

**سرعت استنتاج عامل**: Q4_K سریع‌ترین زمان پاسخ‌دهی عامل روی CPUهای موبایل را ارائه می‌دهد، Q5_K نسبت سرعت به کیفیت متعادلی برای برنامه‌های کلی عامل فراهم می‌کند، Q8_0 کیفیت برتری برای وظایف پیچیده عامل دارد، و فرمت‌های آزمایشی بیشترین توان عملیاتی را برای سخت‌افزار تخصصی عامل ارائه می‌دهند.

**نیازمندی‌های حافظه عامل**: سطوح کوانتیزاسیون برای عوامل از Q2_K (کمتر از ۵۰۰ مگابایت برای مدل‌های کوچک عامل) تا Q8_0 (تقریباً ۵۰٪ اندازه اصلی) متغیر است، در حالی که پیکربندی‌های آزمایشی بیشترین فشرده‌سازی را برای محیط‌های عامل با منابع محدود به دست می‌آورند.

## چالش‌ها و ملاحظات برای عوامل SLM

### مصالحه‌های عملکرد در سیستم‌های عامل

استقرار عامل SLM نیازمند بررسی دقیق مصالحه بین اندازه مدل، سرعت پاسخ‌دهی عامل و کیفیت خروجی است. در حالی که Q4_K سرعت و کارایی استثنایی برای عوامل موبایل ارائه می‌دهد، Q8_0 کیفیت برتری برای وظایف پیچیده عامل دارد. Q5_K تعادلی مناسب برای اغلب برنامه‌های کلی عامل است.

### سازگاری سخت‌افزاری برای عوامل SLM

دستگاه‌های مختلف لبه قابلیت‌های متفاوتی برای استقرار عامل SLM دارند. Q4_K روی پردازنده‌های پایه برای عوامل ساده بهینه اجرا می‌شود، Q5_K منابع محاسباتی متوسطی برای عملکرد متعادل عامل نیاز دارد و Q8_0 از سخت‌افزارهای پیشرفته‌تر برای قابلیت‌های پیشرفته عامل بهره می‌برد.

### امنیت و حریم خصوصی در سیستم‌های عامل SLM

در حالی که عوامل SLM پردازش محلی را برای حفظ حریم خصوصی بهتر امکان‌پذیر می‌کنند، باید اقدامات امنیتی مناسب برای حفاظت از مدل‌ها و داده‌های عامل در محیط‌های لبه به کار گرفته شود. این موضوع به ویژه هنگام استقرار فرمت‌های عامل با دقت بالا در محیط‌های سازمانی یا فرمت‌های فشرده عامل در برنامه‌هایی که داده‌های حساس را پردازش می‌کنند اهمیت دارد.

## روندهای آینده در توسعه عامل SLM

چشم‌انداز عامل SLM با پیشرفت‌های تکنیک‌های فشرده‌سازی، روش‌های بهینه‌سازی و استراتژی‌های استقرار لبه همچنان در حال تحول است. توسعه‌های آینده شامل الگوریتم‌های کوانتیزاسیون کارآمدتر برای مدل‌های عامل، روش‌های فشرده‌سازی بهبود یافته برای فرآیندهای کاری عامل، و یکپارچگی بهتر با شتاب‌دهنده‌های سخت‌افزاری لبه برای پردازش عامل خواهد بود.

**پیش‌بینی‌های بازار برای عوامل SLM**: طبق تحقیقات اخیر، خودکارسازی مبتنی بر عامل می‌تواند ۴۰ تا ۶۰٪ وظایف شناختی تکراری در جریان‌های کاری سازمانی را تا سال ۲۰۲۷ حذف کند، و SLMها به دلیل بهره‌وری هزینه و انعطاف‌پذیری در استقرار پیشگام این تحول خواهند بود.

**روندهای فناوری در عوامل SLM**:
- **عوامل تخصصی SLM**: مدل‌های حوزه‌محور آموزش‌دیده برای وظایف و صنایع خاص
- **محاسبات عامل لبه**: قابلیت‌های عامل بهبود یافته روی دستگاه با حریم خصوصی افزایش یافته و تأخیر کمتر
- **هماهنگی عامل**: هماهنگی بهتر بین چند عامل SLM با مسیر‌یابی پویا و متعادل‌سازی بار
- **دموکراتیزه شدن**: انعطاف‌پذیری SLM مشارکت گسترده‌تر در توسعه عامل را در سازمان‌ها ممکن می‌سازد

```python
    model_provider="foundry-local",
    model_alias="phi-4-mini",
    offline_mode=True
)

# ایجاد و پیکربندی نماینده
agent = Agent(
    config=config,
    model_endpoint=foundry.endpoint,
    api_key=foundry.api_key
)

# تعریف یک ابزار ساده
@agent.tool
def get_current_time() -> str:
    """Get the current time."""
    from datetime import datetime
    return datetime.now().strftime("%Y-%m-%d %H:%M:%S")

# آزمایش نماینده
response = agent.chat("What time is it?")
print(response)
```

### گام ۴: تعیین حوزه و نیازهای عامل
با برنامه‌های عامل متمرکز و تعریف‌شده خوب با استفاده از Microsoft Agent Framework شروع کنید:
- **عوامل حوزه‌واحد**: خدمات مشتری یا زمان‌بندی یا تحقیق
- **اهداف واضح عامل**: اهداف مشخص و قابل اندازه‌گیری برای عملکرد عامل
- **ادغام ابزار محدود**: حداکثر ۳ تا ۵ ابزار برای استقرار اولیه عامل
- **مرزهای تعریف‌شده عامل**: مسیرهای تصعید واضح برای سناریوهای پیچیده
- **طراحی اول لبه**: اولویت دادن به عملکرد آفلاین و پردازش محلی

### گام ۵: پیاده‌سازی استقرار لبه با Microsoft Agent Framework

**پیکربندی منابع**:

```python
from microsoft_agent_framework import ResourceConfig
```

**استقرار تدابیر ایمنی برای عوامل لبه**:
- **اعتبارسنجی ورودی محلی**: بررسی درخواست‌ها بدون وابستگی به ابر
- **فیلتر خروجی آفلاین**: اطمینان از کیفیت پاسخ‌ها به صورت محلی
- **کنترل‌های امنیتی لبه**: اجرای امنیت بدون نیاز به اتصال اینترنت
- **نظارت محلی**: رصد عملکرد و نشانه‌گذاری مشکلات با استفاده از تله‌متری لبه

### گام ۶: اندازه‌گیری و بهینه‌سازی عملکرد عامل لبه
- **نرخ‌های تکمیل وظایف عامل**: رصد میزان موفقیت در سناریوهای آفلاین
- **زمان پاسخ‌دهی عامل**: اطمینان از پاسخ‌های کمتر از یک ثانیه برای استقرار لبه
- **استفاده از منابع**: رصد حافظه، CPU و مصرف باتری در دستگاه‌های لبه
- **بهره‌وری هزینه**: مقایسه هزینه‌های استقرار لبه با گزینه‌های مبتنی بر ابر
- **قابلیت اطمینان آفلاین**: اندازه‌گیری عملکرد عامل در هنگام قطعی شبکه

## نکات کلیدی برای اجرای عامل SLM

1. **SLMها برای عوامل کافی هستند**: برای بیشتر وظایف عامل، مدل‌های کوچک عملکردی برابر با مدل‌های بزرگ دارند در حالی که مزایای قابل توجهی ارائه می‌دهند
2. **بهره‌وری هزینه در عوامل**: اجرای عوامل SLM ده تا سی برابر ارزان‌تر است، که آن‌ها را از نظر اقتصادی برای استقرار گسترده قابل قبول می‌سازد
3. **تخصصی‌سازی برای عوامل موثر است**: SLMهای تنظیم‌شده ظریف اغلب در برنامه‌های خاص عامل از مدل‌های کلی LLM بهتر عمل می‌کنند
4. **معماری ترکیبی عامل**: از SLM برای وظایف روزمره عامل و از LLM برای استدلال پیچیده زمانی که لازم است استفاده کنید
5. **Microsoft Agent Framework امکان استقرار تولیدی را فراهم می‌کند**: ابزارهای سطح سازمانی برای ساخت، استقرار و مدیریت عوامل لبه را ارائه می‌دهد
6. **اصول طراحی اول لبه**: عوامل با قابلیت آفلاین و پردازش محلی حریم خصوصی و قابلیت اطمینان را تضمین می‌کنند
7. **یکپارچگی Foundry Local**: اتصال روان بین Microsoft Agent Framework و استنتاج مدل محلی
8. **آینده متعلق به عوامل SLM است**: مدل‌های زبانی کوچک با چارچوب‌های تولیدی آینده هوش مصنوعی عاملانه و استقرار دموکراتیک و کارآمد عامل‌ها را ممکن می‌کنند
